# 招聘值守台无人值守运行手册

本手册只处理系统可靠性问题。不要直接在数据库中把 `UNKNOWN` 改回 `READY`，也不要对发送结果未知的消息自动重试，否则可能向候选人重复发送。

## 启动监控

```bash
docker compose --profile monitoring up -d prometheus
docker compose ps
```

Prometheus 只在 Compose 内部网络抓取后端指标，默认不映射宿主机端口。需要接入企业告警渠道时，再为 Alertmanager 配置企业微信、飞书或邮件接收器。

## 后端不可用

1. 运行 `docker compose ps`，确认数据库和后端的健康状态。
2. 运行 `docker compose logs --since=10m backend`，定位最近一次启动或运行错误。
3. 后端恢复后，持久队列会自动回收超时的处理中任务；不要手工复制任务。

## 队列持续积压

1. 在“项目运行日志 → AI 自动回复队列”确认等待数和最早等待时间。
2. 检查 AI 服务是否可用、模型耗时是否升高，以及可用 AI 槽位是否长期为 0。
3. 不要通过提高发送上限解决 AI 服务故障。容量调整应先压测，再逐级提高并发。

## 任务等待超时

最早任务超过 3 分钟说明消费链路可能停滞。检查后端日志中的模型超时、数据库连接和任务领取冲突。系统会回收超过 180 秒的 `PROCESSING` 任务并进入受控重试。

## 发送结果不确定

`UNKNOWN` 表示插件在领取发送租约后未能提供可信回执。系统刻意禁止自动重试。

1. 由 HR 打开对应会话，人工核对消息是否已经发送。
2. 记录实际结果并人工处理；不要修改数据库绕过幂等保护。
3. 若连续出现 3 次，插件断路器会停止持续回复。排除页面 DOM 或网络问题后，由用户手工重新开启。

## 重试任务持续增加

检查 AI API 的超时、限流和响应格式错误。临时模型失败采用有限次数与退避重试；同账号 AI 最多并发 3 条，页面发送仍逐条串行，不应手工重复提交相同消息。事实不匹配、岗位无关和正常静默不是模型故障，不应因库存复核而反复调用 AI。

## AI 并发饱和

并发槽位连续耗尽时，先观察模型 P95/P99 延迟和队列增长速度。只有模型服务与数据库均稳定时才逐级调整 `APP_INBOUND_REPLY_MODEL_CONCURRENCY`；有效范围被后端限制为 1～64。同账号 AI 分析最多并发 3 条，BOSS 页面仍只允许一次定位并逐条发送；发送前必须重新复核最新消息摘要和方向，防止旧分析结果误发。

## 浏览器桥接不可用

1. 确认 Chrome 和 BOSS 页面仍在运行，电脑没有休眠或断网。
2. 在“招聘账号”查看桥接状态、最近心跳与停止原因。
3. 若插件触发断路器，先人工核对最近一条消息是否已发送，再由用户重新开启持续回复。
4. 只有用户明确允许时才重新加载扩展；自动化程序不得擅自控制 BOSS 浏览器。

扩展会持久化最多 500 组匿名会话/消息摘要基线，并串行写入运行态。页面刷新或内容脚本重载后会恢复未完成 AI 任务及既有基线；已点击发送但回执不明的任务只做限时、同会话的只读复核，不会重新点击。基线与复核证据不保存候选人姓名或消息正文。

## 自动发送开关关闭

这是安全告警而非数据丢失。队列生成的回复会停留在 `READY`。确认环境和账号允许自动发送后，将 `APP_INBOUND_REPLY_AUTO_SEND_ENABLED=true` 并重建后端；不要直接修改数据库任务状态。

账号达到每小时或每日发送上限时同样保留 `READY`，插件以至少 60 秒间隔重新检查；额度窗口恢复后才签发发送租约。限流不得把任务永久改为 `SKIPPED`，也不得通过提高插件轮询频率绕过。

`READY` 和 `CLAIMED` 也计入账号/全局队列上限，防止模型生成速度高于页面发送速度时无界积压。历史清理只删除真正终态的任务；未发送的 `READY` 和尚在租约内的 `CLAIMED` 不受 7 天历史保留期影响。

## JVM 内存持续偏高

先检查队列深度、处理中任务以及请求速率是否同步增长。不要只靠重启掩盖持续泄漏；保留 Prometheus 时间序列和最近 30 分钟后端日志，再检查堆内存是否能在流量下降后回落。

## 数据库连接池等待

检查慢 SQL、数据库 CPU/IO 和连接占用。AI 公网调用不应持有数据库事务；若等待持续存在，应先定位长事务，再评估连接池大小，禁止无依据地同时扩大连接池和 AI 并发。

## 后端反复重启

1. 使用 `docker compose ps` 与 `docker inspect` 查看退出状态、OOM 和健康检查。
2. 使用 `docker compose logs --since=30m backend` 保留故障上下文。
3. 依赖持久队列恢复处理中任务，不要复制或重新插入任务。

## 部署与停机边界

后端使用优雅停机：停止接收新请求后，最多等待 70 秒完成运行中的请求，内部 AI worker 最多等待 65 秒。Compose 为后端保留 75 秒停止宽限期。超过宽限期的处理中任务仍由持久队列在启动后安全回收。

## 安全停机

将 `APP_INBOUND_REPLY_AUTO_SEND_ENABLED=false` 后重建后端。已生成回复会保留为 `READY`，插件不会领取新的发送租约。确认风险解除后再恢复开关。

## 每日检查

- 后端、数据库、Web 容器均为 healthy。
- 每条 `UNKNOWN` 都有明确的人工复核记录；不得出现未知结果后重复点击发送。自动发送允许且 BOSS 页可见时，最早 `READY` 等待时间不应持续超过 180 秒。
- 失败与重试没有持续增长。
- Chrome 扩展版本与代码版本一致，且没有触发本地断路器。
- 已约面会话保持人工跟进，不进入自动回复队列。

## 新版本连续运行验收（尚需在真实 BOSS 页面执行）

代码测试通过不等于真实页面的长期验收。先在允许测试的账号和会话上观察，再进入连续 72 小时运行；保留插件状态条日志、`/api/local-connector/ai-duty-events` 和 `/api/local-connector/ai-reply-quality-summary` 的定期快照（均按现有权限访问，不在报告中复制候选人原文或设备令牌）。每次刷新、扩展重载、模型超时和人工暂停都记录时间，以便区分系统故障与人为停机。

验收期间逐日复核以下项目：

1. 安全底线：错会话发送、重复发送均为 0；`UNKNOWN` 只读复核或转 HR，不自动重发；面试安排始终转 HR。
2. 连续性：可见沟通页中长列表扫描会继续推进，`LIST_SCAN_PARTIAL` 不误报为无未读；`READY` 优先发送，队首不可定位会话不会永久阻塞后续任务。
3. 简历与页面：PDF 处理后确认预览消失才切换会话；关闭失败时停机并显示原因；隐藏或最小化窗口明确显示暂停，恢复可见后重新复核最新消息。
4. 回复质量：按 `dispositionCode` 统计正常静默、事实拦截、面试人工、模型临时失败和最终失败。每天抽查可回复却被静默的样本，只调整规则并加回归测试，不直接把所有静默改成发送。
5. 效率：记录发现来信、AI 完成、`READY`、发送确认四个时间点，分别看 P50/P95 和最长等待；若 `READY` 在页面可见且自动发送允许时持续超过 180 秒，按队列定位、页面 DOM、租约和回执四段排查。

刷新页面、预览关闭失败、模型超时和发送回执丢失的故障演练只在测试账号/测试会话中进行；不要为了制造故障而向真实候选人重复发送。72 小时内若安全底线不满足，暂停自动发送、保留诊断证据并修复后重新计时。

先在本地重载新版扩展、保持 BOSS 沟通页可见，并由 HR 开启测试账号的托管；确认桥接心跳正常后，在项目目录执行：

```bash
sh scripts/run-unattended-soak.sh 259200 30 /private/tmp/recruitment-soak
```

脚本默认要求后端自动发送总开关、至少一个正在托管的账号，以及至少一个未过期心跳的桥接设备；没有真实托管时会失败，不能用空跑代替验收。它以首个有效采样的历史 `UNKNOWN` 为基线，只对监测期间新增的未知发送报警。只验证容器、队列、模型槽位、设备心跳和回执计数；错会话、回复质量、预览关闭及 BOSS 页面是否始终可见，仍须结合插件阶段日志和 HR 抽样复核。仅检查基础设施时可显式设置 `SOAK_REQUIRE_ACTIVE_DUTY=0`，其结果不算自动回复验收。
