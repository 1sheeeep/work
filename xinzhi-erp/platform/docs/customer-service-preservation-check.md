# 生产客服接入保护与验收门槛

2026-09-06：**离线快照比对工具与只读候选切片已实现；完整接入准备未完成，正式接入仍为 NO-GO。**

客服正在生产使用。目标是先把正常路径、异常路径和恢复路径验证清楚，再在明确范围内接入；不承诺绝对零故障，也不允许把“可以部署准备版本”解释为可以试改生产。范围遵循 [接入准备](production-customer-service-integration-preparation.md)。

采用小范围放行、逐阶段健康检查、发现问题停止扩大、保留可验证恢复路径的成熟发布方式；有状态数据的恢复不能简单等同于回退程序版本。[安全部署参考](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/safe-deployments)

## 1. 正式接入前必须关闭的条件

以下任一项未执行、失败、证据与发布版本不一致或仍有未解释差异，就不放行。它们不是已经打勾的验收结果。

| 保护面 | 必须验证 | 当前证据状态 |
|---|---|---|
| 原账号、密码与权限 | 主键保留，密码不覆盖，停用状态不恢复，坐席/角色/店铺范围不扩大；同邮箱不同人不自动合并；ERP 登录不让坐席上线 | 离线差异检测、实际 Java + Go + 两份合成 PostgreSQL 身份/会话与权限联调通过；真实采集与真实账号验收未执行 |
| 原聊天与邮件 | 插件消息、邮件收发、领取/回复/转交/结束、工单、断线重连；接入前已存在的会话持续可用；不重复发送、漏收或误结束会话 | 未完成新架构的实际服务演练和人工验收 |
| 原店铺与授权 | 店铺/应用/安装引用、实际授权、渠道路由保留；候选通道默认不启用；未核验 scope 不放开操作 | 离线引用/scope 差异检测、候选只读适配与合成上游身份/scope 拒绝已验证；未核验真实店铺或生产通道 |
| 历史数据 | 账号、会话、消息、工单、分配、审计的主键/关系及保护列完整；不能只核对表行数 | 合成快照可识别数量不变但摘要改变；真实采集器和历史保护列清单未完成 |
| 双通道写入 | 幂等、资源冲突、断网超时、重启恢复、事件重复/乱序、写入结果待核对阻断切换 | 未完成；快照工具不能替代写入故障测试 |
| 接入与回退演练 | 精确候选版本在隔离 Java + Go + 临时数据库中完整走正常接入、失败回退；校验新消息/新订单不因回退丢失 | 身份子集通过：停止候选通道后原客服会话有效、备份后的新消息保留；完整写入与聊天邮件业务回退尚未完成 |
| 备份可恢复 | 原库/配置的备份归属、完整性及恢复步骤核对，在隔离实例实际恢复并校验权限与关联 | 新身份切片已将两份合成库恢复到另外两份空库，核对表摘要、原客服权限启动与原会话；未核验真实生产备份，旧 UAT 39 表记录不代替此项 |
| 发布与业务观察 | 固定发布对象、旧版本、依赖、资源余量、错误/延迟/队列基线；覆盖正常及高峰使用，不只看容器健康 | 未核验线上；观察窗口、阈值及最大允许恢复时间须在正式操作前确定，不填猜测数字 |
| 操作授权 | 用户明确通知正式接入并确定账号/店铺范围；身份/店铺对应关系确认，人工业务验收有记录 | 当前仅允许不影响既有使用的准备性部署 |

正式操作时保留每项证据的精确源码/镜像版本、环境、时间、输入快照摘要、实际结果和确认人；不能用旧版本的绿灯覆盖新版本。账号/权限异常、聊天或邮件回归失败、历史差异、待核对写入、恢复失败均为停止条件，不临时添加“忽略差异”来通过。

恢复优先停止新接入通道并按已演练方案恢复原路由/程序，原客服保持其数据所有权。**不得直接恢复旧数据库覆盖切换后产生的新消息、工单或订单。** 对已提交或结果未知的写入先核对再处理；备份存在本身不证明可以安全整库回滚。生产高峰不用于压测，原应用不提前卸载，UAT 不提前删除。

## 2. 本轮可执行的最小保护检查

实现：[customer-service-preservation-check.mjs](../scripts/customer-service-preservation-check.mjs)。
测试：[customer-service-preservation-check.test.mjs](../scripts/customer-service-preservation-check.test.mjs)。

只读取操作者明确指定的两个本地 JSON 快照，比对相同环境、企业、保护集合和历史截止点；没有网络访问、凭据读取、自动采集、数据库修改或部署调用。不接入应用启动、构建或现有发布脚本。复用项目已有 Node 内置测试方式，没有新增依赖。[Node 测试说明](https://nodejs.org/api/test.html)

运行格式（两个文件需先由已审查的采集过程生成，本轮未生成真实快照）：

```text
node platform/scripts/customer-service-preservation-check.mjs --before ./before.json --after ./after.json
```

| 返回值 | 含义 | 可以据此做什么 |
|---|---|---|
| `0 / SNAPSHOTS_MATCH` | 提供的保护记录一致 | 只记录这一项比较结果；不代表生产就绪 |
| `1 / DRIFT_DETECTED` | 记录增加、缺失或字段改变 | 停止放行并核对差异 |
| `2 / INVALID_INPUT` | 文件不可读、格式/覆盖不完整、企业或截止点不同、重复记录、无效关联、复用同一采集等 | 修复采集或输入，不能当作无差异 |

所有结果固定含 `comparisonOnly=true`、`sourceAuthenticityVerified=false`、`productionReady=false`。报告仅包含固定错误码、集合、零起始位置、变更字段及有效输入对的文件 SHA-256；无效输入不输出文件摘要，避免误传凭据文件时输出其派生信息。不回显账号/店铺标识、权限值、文件路径、Secret 或解析异常正文。保存报告时应同时保留受控原始快照供定位，不把报告误用为自动上线信号。

没有忽略差异或强制通过参数。输入只接受普通文件，单文件最多 2 MiB；未知字段、缺集合、重复权限/scope、重复 Shopify 店铺映射、无效角色/渠道店铺引用都会拒绝。超出容量不能通过截取几页数据冒充完整快照。

## 3. 快照约定（离线核对格式，不是生产接口或迁移表）

根对象只包含以下元信息和五个记录集合；具体合成样例在测试文件的 `snapshots()` 中。`ref` 等标识只用稳定内部引用，不填姓名、邮箱、密码或 Token。

| 元信息 | 要求 |
|---|---|
| `schemaVersion` | 固定 `1` |
| `environment` | `synthetic`、`isolated` 或 `production`；两次相同，字段只声明来源，不验证真实性 |
| `enterpriseRef` / `baselineRef` | 同一企业与同一经确认的保护集合；两次相同 |
| `captureRef` / `capturedAt` | 两次必须为不同采集标识；后采集严格晚于前采集；时间为带毫秒的 UTC ISO 格式 |
| `historyCutoff` | 两次相同，且不晚于采集时间；用于排除截止点以后正常新增的历史记录 |
| `complete` | 必须为 `true`；仅为采集者声明，工具无法证明没有漏页或人为遗漏 |

| 集合 | 每条必填字段 | 保护含义 |
|---|---|---|
| `users` | `ref`、`status`、`roleRefs`、`scopeDigest` | 原账号主键/状态/角色及完整数据范围；摘要须涵盖实际版本中的店铺、工作台、会话等全部权限范围 |
| `roles` | `ref`、`permissionCodes` | 不允许角色权限被静默替换、删除或扩大 |
| `shops` | `ref`、`status`、`shopifyShopRef`、`appRef`、`installationRef`、`grantedScopes` | 原店铺与授权引用；后三个引用字段可为 `null`，scope 未知为 `null`，已知空为 `[]`，二者不能混同 |
| `channels` | `ref`、`shopRef`、`kind`、`enabled`、`configurationDigest` | `kind` 为 `email` 或 `chat`，`shopRef` 可为 `null`；保护渠道归属、开关及非敏感配置摘要 |
| `history` | `kind`、`recordCount`、`digest` | 必须分别包含 `conversations`、`messages`、`tickets`、`assignments`、`audit`，同时比较数量和保护列摘要 |

摘要为小写 64 位 SHA-256。采集器须在受控源端规范化字段、排序记录和集合后计算；历史摘要必须覆盖原主键、关联和已确认保护列，不能只把行数散列一遍。摘要算法、保护列和字段版本要随 `baselineRef` 固定；当前尚未实现或核验真实采集器。用户角色、权限、scope 数组按集合比较，记录与字段排序不影响结果；新增或缺失记录仍报差异。

生产持续产生新消息，前后采集不能简单全表扫完就相互比较。须用一致性读取、固定截止点及经过核对的保护集合；截止点以后的正常业务增长另行验收。原有记录的合法可变字段（如接待在线状态、工单状态）要与应保持不变的字段分开，并在业务回归中验证。合法管理员变更若影响保护基线，也须核对并重新建立经审查的基线，不能自动忽略。

快照不接受密码、密码散列、API Secret、访问/会话 Token 或客户消息原文。密码和真实会话是否保留需要临时库身份演练及用户人工登录验证；本工具不证明这两项。它也不能证明摘要内容计算正确、实际 scope 可用、聊天/邮件可收发、数据采集真实完整，或系统性能满足要求。真实快照与采集实现须另行审查，敏感原始证据不得提交仓库。

## 4. 当前实测与下一步

- Node `v24.16.0`，本工具 60 项测试通过，零失败/跳过；包含真实命令行执行、输入不被修改、异常输出不泄露数据、无效输入拒绝和上述差异用例。
- 与既有共享登录前端/API 及 Windows 测试门禁一起运行，4 个文件共 81 项通过。只读候选另有真实 Java + Go 进程测试及合成浏览器检查；数据库与全量后台最终结果统一见 DEV_STATE。真实账号/店铺验收未执行。
- 只使用合成内存对象和本轮独占临时文件；测试结束仅删除两份测试输入和空临时目录，不递归清理用户目录。
- 新增的只读候选应用代码和测试见 [演练说明](store-app-read-preparation-rehearsal.md)，默认关闭且未挂载客服生产入口；未触碰生产凭据、数据库、部署配置或在线服务，未提交、未部署。

只读候选是 [接入准备](production-customer-service-integration-preparation.md) 的一个切片；还必须逐项完成身份、写入/切换、完整隔离演练和真实基线采集。当前工具及读取测试都不能充当“一次接入成功”的证据。
