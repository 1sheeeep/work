## 1. 已确认目标与本轮边界

- 同一个企业、多个业务：以原生产客服的既有账号为保留基准，ERP 账号经过核对后关联并入；保留客服密码、账号主键、坐席权限、店铺范围、历史记录和原有网址。
- ERP 与客服保留各自业务工作台、业务数据库和会话。统一身份不等于合并数据库，不恢复 One，不在 ERP 重做客服页面，不使用 iframe 嵌入客服。
- 店铺应用继续在客服新增和授权；SaaS 公开应用继续在 ERP 新增和授权。两个入口对应同一份店铺映射，不建立两套同名业务店铺。
- ERP 必须能够依据有效店铺应用授权执行已批准的真实读取和写入，不以展示客服缓存代替接入。客服也应能通过现有 SaaS Connector 使用 SaaS 授权。
- 每店铺明确一个当前业务读写通道；另一个可处于待核验或切换准备状态。聊天插件的归属另外核对，不能随业务通道切换自动卸载旧应用。
- 目标是日常使用平滑切换，不承诺绕过 Shopify 人工安装/增权，也不承诺保留所有旧 ERP 会话。
- 复制客服 UAT 已获准立即停止并保留全部数据；删除须等原生产客服完全接入并验证闭环，不以容器健康或已开通账号替代这一条件。

已整理契约、映射模板、能力缺口和验证顺序，并标记旧文档；[数据保护检查](customer-service-preservation-check.md) 已有独立离线快照比对工具。[店铺应用只读候选切片](store-app-read-preparation-rehearsal.md) 已实现明确店铺绑定、实际授权核验、订单预览、默认关闭的 ERP 页面及受限服务适配器。[身份接入隔离演练](customer-service-identity-preparation-rehearsal.md) 已补持久人员核对/审计、两端撤销版本、加密租约、独立 ERP 会话、同源表单与双库恢复测试；未挂载现有登录入口，真实浏览器完整流程仍未通过，不是已上线 SSO 或真实账号迁移。本地库存持久命令、两来源客户端与冻结核验已补齐，正式全业务路由与写入切换仍未实现。新增 SQL 仅显式用于独占临时库，不在自动迁移目录；未配置真实服务地址、读取凭据、连接生产、合并真实账号、发布或切换流量。全部永久排除及暂停范围继续受 [锁定产品范围](locked-product-scope-boundaries.md) 约束。

部署与启用生产接入分开。以下保留为后续在明确授权目标内发布的必要条件，不构成当前操作生产客服的许可；当前接入准备部署与正式接入都保持关闭。

- 用既有流程验证当前登录、会话、角色、店铺授权及业务行为保持兼容；不能只隐藏前端入口，就声称新增代码不会运行。新通道必须默认不启用，无隐式迁库、账号初始化、生产回补或外连任务。

- 保留旧版本与可验证回退路径，限定替换对象并检查受保护对象未变化。涉及不可兼容数据迁移、现有会话失效、共享服务中断或无法说明影响时，停止发布并告知用户，不把有条件许可当作无条件发布授权。
- 发布后分别记录服务健康、原有链路回归和新切片验证；不以“容器启动”代替业务可用性。不改变生产客服入口、实际店铺授权/插件、账号映射；UAT 仅按最新明确授权停止，删除等待完整接入。

## 3. 非敏感映射模板

以下是将来核对表的字段约定，不是数据库迁移脚本或可加载配置。本轮没有填入任何真实关联。示例只使用 `fixture-enterprise`、`fixture-cs-user-1`、`fixture-erp-user-1`、`fixture-shop-1` 等合成标识。

### 企业与账号

| 字段组 | 必须记录 | 拒绝或人工核对条件 |
|---|---|---|
| 企业 | `enterpriseRef`、既有 ERP `tenantId`、客服现有企业/数据分区引用、核对证据 | 不凭输入 `xz` 或同一个域名自动建立企业成员关系；原客服无显式 tenant 字段时不得假造已完成租户迁移 |
| 人员关联 | 稳定 `subjectRef`、原客服 `userId`、可选 ERP `userId`、确认人/时间/证据、映射版本 | 同邮箱不同人、同人多个账号、一个业务账号被重复关联、企业不匹配：标记 `CONFLICT`，禁止登录时自动合并 |
| 原有业务事实 | 两端原始角色、停用状态、店铺范围、历史操作人 ID 的引用 | 保留原值；不得以角色并集、管理员继承或“同企业”扩大权限 |
| 关联状态 | `UNREVIEWED` / `CONFLICT` / `CONFIRMED` / `DISABLED` | 只有核对通过、对应业务开通且原业务账号有效才允许访问；关联不自动开通另一业务 |
| 凭据归属 | 仅记录由哪一端验证，不记录密码、散列、会话或密钥 | 保留客服密码；ERP-only 账号如何并入需列入正式迁移核对，不静默覆盖或重置凭据 |

同一人员可以关联两个既有业务账号，但历史订单、会话、工单和审计中的原始操作人 ID 不回写。映射提供溯源，不替换历史事实。业务停用与统一身份停用应分别建模；任一禁止访问的状态不能被另一端启用状态覆盖。

### 店铺与授权来源

| 字段组 | 必须记录 | 拒绝或核对条件 |
|---|---|---|
| 稳定店铺 | `enterpriseRef`、`canonicalShopRef`、原 ERP `shopId`、原客服 `shopId`、经授权服务验证的 Shopify Shop ID、规范店铺域名 | 不凭店铺显示名合并；域名只是定位线索；同一企业同一 Shopify 店铺出现冲突关联时停止 |
| 授权来源 | `providerRef`、`sourceKind`（准备术语 `CS_STORE_APP` / `ERP_SAAS_APP`）、非敏感应用引用、非敏感安装引用、凭据所有者 | 安装必须与企业和店铺映射一致；不得把客户端传入的店铺 ID 当作授权依据 |
| 能力快照 | 实际 `grantedScopes`、验证时间、可用操作、缺失条件、授权状态 | 未核验或空的 scope 信息为未知，不按默认配置视为全部授权 |
| 运行路由 | 当前 `activeProviderRef`、`routeVersion`、候选来源、同步检查点、待核对命令数、原插件来源 | 不能由一个全局环境开关切换全部店铺；候选来源不执行影子写入 |

本轮新增只读候选 `ConnectorMode` 标记，但不新增数据库字段，不改变现有业务来源。以上正式映射/路由名称仍是后续契约词汇，候选绑定版本不能当作已实现正式切换版本。实现继续复用既有店铺主键、接口、审计与幂等机制，避免再造身份平台或通用插件框架。

## 4. 两条接入通道的最小接口约定

### 所有权

| 内容 | 店铺应用通道 | SaaS 应用通道 |
|---|---|---|
| 新增、安装及增权入口 | 原客服 | ERP |
| OAuth、Token、应用 Secret、Webhook 验签 | 原客服的应用接入服务 | 现有独立 SaaS Connector |
| ERP 如何使用 | 由现有 `ChannelConnectorGateway` 的新适配器调用受控服务接口 | 继续使用既有 Connector 适配器 |
| 客服如何使用 | 保留当前服务内实现及业务行为 | 通过受控接口调用 SaaS Connector，不复制 Token |
| 身份与范围 | 企业、操作者/任务权限、店铺关联、操作能力逐项校验 | 同左；安装存在不等于账号具备业务权限 |

服务调用只传业务操作和非敏感引用；不向 ERP、浏览器、映射清单或日志输出原客服 Shopify 凭据。不共享用户浏览器 Cookie，不使用常驻管理员登录态，也不直连对方业务表来代替接口。

### 目标服务契约与当前实现范围

下表是完整目标。“授权状态/能力核验”和“一页订单读取”已有默认关闭的 ERP GET 路由与未挂载到生产的客服适配器；具体限制见 [只读演练说明](store-app-read-preparation-rehearsal.md)。身份候选已实现显式持久绑定、独立会话、可靠版本撤销及同源表单，自动化验证通过，真实浏览器完整流程和生产兼容仍未验收；见 [身份演练说明](customer-service-identity-preparation-rehearsal.md)。库存持久写入/原来源核对与冻结核验已有未挂载候选；仅客服人员独立权限和 Java → Go 客户端合成上游闭环通过，正式全业务路由仍未实现。

| 契约 | 最小输入 | 最小输出与要求 |
|---|---|---|
| 身份验证/业务会话兑换 | 可信服务身份；受限目标业务；短时、单次、绑定来源/目标/浏览器/企业的凭证 | 稳定人员引用、企业、映射/撤销版本；目标业务重新检查本地权限并创建自己的会话；纯身份验证不得使坐席上线 |
| 授权状态/能力核验 | 企业、稳定店铺、授权来源 | 授权状态、实际 scope、可执行操作、缺失条件和 `checkedAt`；不返回 Token |
| 业务读取 | 企业、稳定店铺、有效人员或受限同步任务、操作名、分页条件 | 复用 ERP 现有 DTO；带授权来源、路由版本、获取时间与数据同步时间；陈旧缓存不能伪装成实时读取 |
| 业务命令 | 同上，另含 `commandId` / 幂等键、操作前置条件、`expectedRouteVersion` | `APPLIED` / `REJECTED` / `PENDING` / `UNKNOWN` 的统一语义及回执；具体接口可保留既有结果类型，不把准备术语硬塞入所有 DTO |
| 命令核对 | 企业、稳定店铺、原 `commandId` 及原授权来源 | 返回同一命令的最终/待核对状态；不得切换来源后重新执行 |

身份传输协议在实现切片时结合两端现有依赖确定；以上只是必须满足的安全性质，不声明已经支持 OIDC。企业管理员与平台管理员必须使用不同含义的字段，不能沿用旧 `systemAdmin` 歧义。浏览器提交的企业、人员、角色和来源均不可信，须由受认证服务核验；服务身份与用户身份不能互相替代。后台同步任务采用受限业务授权，不能冒充管理员。

保留账号密码直登、减少可见跳转的体验目标。共享身份后，两端仍持有独立会话；凭证不得出现在 URL、浏览器持久存储或日志中。重放、过期、跨企业、跨目标、映射变化、账号停用或业务撤权均拒绝；认证服务不可用时不放宽权限。ERP 登录/退出不能隐式开始或结束客服接待。是否支持全业务退出及其传播时限，在会话切片中明确并验证，不能把“退出一个工作台”描述为全局退出。

复用安全请求、限频、授权检查与审计，不提供接受任意 URL、GraphQL 或管理员指令的万能代理。仅开放当前切片所需的白名单操作。

统一区分：未授权、能力不足、关联冲突、业务权限不足、限流、服务不可用、路由版本冲突、写入结果待核对。超时和服务不可用不等于授权撤销；错误中只保留安全码和关联编号，不透传密码、Token、请求头或敏感响应。

## 5. Shopify 能力缺口清单

以下来自既有 ERP 契约和前序检查的原客服源码默认 scopes，**不是任何真实店铺的权限检测结果**。每项正式可用性还取决于接口实现、实际安装授权、资源归属和业务权限。

| 操作 | 核对重点 | 原客服源码默认值线索 | 准备结论 |
|---|---|---|---|
| 商品、地点、库存读取 | `read_products`、`read_locations`、`read_inventory` | 含这些权限 | 等待逐店实际核验及标准 DTO 适配 |
| 订单/客户读取、订单地址修改 | 订单读/写、客户读取及所需受保护数据字段 | 含 `write_orders`、`read_customers` | 不能据默认值确认字段可见或写入可用 |
| 超过默认窗口的历史订单 | 订单读取权限与 `read_all_orders` | 默认未含 `read_all_orders` | 明确记录历史覆盖范围，不能以有最近订单冒充全量 |
| 库存调整 | `write_inventory`、地点/库存项权限和并发前置条件 | 默认只有 `read_inventory` | 写权限与服务适配均需核对；不静默增权 |
| 修改订单商品行/数量/折扣 | `write_order_edits` 与对应业务操作 | 默认未含 `write_order_edits` | 未具备时禁用操作，保留明确补权提示 |
| 履约/物流信息 | 按履约单分配、服务归属核对具体 scope 和接口 | 含若干 fulfillment scopes | 不把其中一个 write scope 解释为所有履约单可操作 |
| 退货退款、拒付元数据 | 原客服业务归属、实际 scopes、可能的员工权限和接口前置条件 | 含 `write_returns`、`read_shopify_payments_disputes` | 沿用已批准归属；不因 Gateway 方法存在而扩展 ERP 范围；不恢复拒付证据读写 |
| 店铺聊天插件 | 应用/扩展/主题绑定、消息路由及渠道身份 | 原应用已有插件流程 | 与业务授权切换分开验收，保留原会话与渠道 |

Shopify 规定写权限包含对应读取权限，超过默认 60 天的订单需要额外的 `read_all_orders` 授权；授权必须检查实际授予列表，不能只看请求配置。[官方权限说明](https://shopify.dev/docs/api/usage/access-scopes)

当前“店铺应用”是本项目的接入渠道称呼。前序源码显示每店铺 App profile + OAuth，并非粘贴 Admin API Token 的旧式实现；不能仅凭源码断言所有真实应用的 Shopify 分发类型。SaaS 与店铺应用保留独立应用身份，不尝试把已选分发方式直接改成另一种。[官方分发边界](https://shopify.dev/docs/apps/launch/distribution/select-distribution-method)

## 6. 平滑切换、事件与故障边界

每店铺的切换准备按以下顺序进行，当前不执行：

1. 核对同一店铺身份及候选授权，满足该店铺已启用业务的全部必要能力；缺权限时保持原来源，不能切后才发现业务被禁用。
2. 候选通道仅做读取校验；建立独立同步检查点，核对订单/商品/库存时间范围及差异。客服已有缓存只能作比较，不能证明 ERP 已获得上游实时访问。
3. 暂停该店铺新命令的下发，并确保两个业务遵守同一切换锁；冻结期间新命令受控排队或明确返回稍后重试，不自动投向另一个来源。
4. 排空/核对已发命令。`UNKNOWN` 或未完成命令必须通过原来源核对；无法确认则停止切换，不双发库存、履约、退款或订单修改。
5. 原子更新该店铺 `activeProviderRef` 与路由版本；两业务确认新版本后恢复下发，旧版本请求拒绝并重新核对，不能绕过冻结。
6. 核对读写回执、事件、同步与客服体验。保留原授权和映射以便回退；回退也必须先核对在途命令，不能自动重复已经生效的操作。

采用跨来源稳定的业务幂等键和持久回执，同一命令只能有一个执行来源。两业务命中同一订单等资源时，还必须检查资源状态/版本或既有并发机制；不同幂等键并不能防止相互冲突的独立操作。进程重启、连接断开或超时不能抹去待核对状态。

同一 App + 同一店铺共享 Shopify API 限额，因此两业务通过同一来源使用时需要共享预算：客服实时查询优先，ERP 历史回补和批量任务低优先，遵循上游成本/限流信息并有限退避；不做生产压测。[官方限流说明](https://shopify.dev/docs/api/usage/limits)

两条通道分别用各自应用 Secret 对原始请求体验签、持久接收，再异步处理。`X-Shopify-Webhook-Id` 用于单次投递去重，`X-Shopify-Event-Id` 用于关联同一动作；不能假定两个应用的每条消息都有可通用去重的同一 ID。[官方 Webhook 说明](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries)

业务层另按稳定店铺、主题、资源和版本做幂等处理，避免跨来源重复生效及乱序回退，并通过增量补拉核对遗漏。接收来源、投递去重键与业务事件处理分层记录，不能把同一事件不同主题全部丢弃。卸载/撤权只影响对应安装；隐私请求仍按其应用归属和实际数据持有范围履行，不能因来源不活跃而忽略。
